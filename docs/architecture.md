# Архитектура

Как устроен проект сейчас. Документ обновляется в той же задаче, что и код (догма 2).

## Пакеты

Проект — монорепозиторий pnpm. Каждый пакет лежит в `packages/`.

| Пакет | Что в нём | От чего зависит |
|---|---|---|
| `@homamru/core` | Ядро: правила игры, состояние, генератор случайных чисел. Работает без окна, в Node и в браузере. | Ни от чего. |
| `@homamru/data` | Схемы контента и разбор файлов JSON и YAML. | `zod`, `yaml`. |
| `@homamru/client` | То, что видит игрок: Phaser (карта, бой), React (окна), вход в приложение. | `@homamru/core`, `phaser`, `react`. |

Позже появится `@homamru/server` для сетевой игры: он запускает то же ядро на Node.

Зависимости идут в одну сторону: `client` → `core`. Ядро не знает ни о Phaser, ни о React, ни о браузере, ни о Node.

Пакеты подключают друг друга прямо исходниками на TypeScript (`exports` указывает на `src/index.ts`), отдельной сборки пакетов нет. Собирается только клиент, через Vite.

## Что сейчас есть в коде

- `packages/core/src/rng.ts` — детерминированный генератор случайных чисел (алгоритм mulberry32). Состояние генератора — обычный объект, который будет храниться в игровом состоянии. Функции возвращают значение и новое состояние, ничего не меняя на месте.
- `packages/data/src/parse.ts` — `parseContentFile`: разбирает текст файла (JSON или YAML по расширению), проверяет по схеме Zod и возвращает либо данные, либо список ошибок с именем файла и поля. С диска не читает.
- `packages/client` — проверочный экран каркаса: Phaser рисует поле клеток, цвета выбирает генератор из ядра, поверх лежит панель на React. Игровых правил в нём нет. Экран будет удалён, когда появится карта.

Игрового состояния, команд, схем контента и самих данных ещё нет: они появятся вместе с первыми спецификациями механик (догма 3).

## Клиент: холст и интерфейс

На странице два слоя: `#game` (холст Phaser) и `#ui` (вёрстка React поверх холста). Слой интерфейса сам не перехватывает нажатия; перехватывают только его видимые элементы.

React и Phaser общаются через реестр игры (`game.registry`): React записывает значение, сцена подписана на его изменение. Напрямую сцены и компоненты друг друга не вызывают.

## Как догмы проверяются автоматически

Всё это запускает одна команда `pnpm run check`; её же запускает CI на каждый коммит.

| Догма | Проверка |
|---|---|
| 5. Ядро отделено | `scripts/check-boundaries.mjs`: у ядра нет зависимостей, его код импортирует только соседние файлы. Линтер запрещает в ядре `phaser`, `react`, `node:*`, `window`, `document`. Проверка типов: ядро собирается без типов браузера и Node. |
| 7. Детерминизм | Линтер запрещает в ядре `Math.random`, `Date`, `performance`, таймеры и `crypto`. Тест генератора сверяет значения с эталоном, посчитанным отдельной реализацией. |
| 8. Контент в данных | `parseContentFile` и его тесты: ошибка называет файл и поле. Проверка всех файлов данных появится вместе с первым типом контента. |
| 9. Тесты | `vitest run` в составе общей проверки. |
| 11. Простой код | Knip ищет неиспользуемые файлы, экспорты и зависимости. Линтер ограничивает файл 300 строками и запрещает `any` и циклические импорты. |

Догмы 6 (команды) и «повтор партии даёт тот же результат» пока проверять не на чем: проверки появятся вместе с игровым состоянием.
