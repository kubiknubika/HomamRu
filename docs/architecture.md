# Архитектура

Как устроен проект сейчас. Документ обновляется в той же задаче, что и код (догма 2).

## Пакеты

Проект — монорепозиторий pnpm. Каждый пакет лежит в `packages/`.

| Пакет | Что в нём | От чего зависит |
|---|---|---|
| `@homamru/core` | Ядро: правила игры, состояние, генератор случайных чисел. Работает без окна, в Node и в браузере. | Ни от чего. |
| `@homamru/data` | Схемы контента и разбор файлов JSON и YAML. | `@homamru/core`, `zod`, `yaml`. |
| `@homamru/cli` | Консоль: проигрывает сценарии, читает файлы с диска. Только для разработки, в игру не входит. | `@homamru/core`, `@homamru/data`, Node. |
| `@homamru/client` | То, что видит игрок: Phaser (карта, бой), React (окна), вход в приложение. | `@homamru/core`, `@homamru/data`, `phaser`, `react`. |

Позже появится `@homamru/server` для сетевой игры: он запускает то же ядро на Node.

Зависимости идут в одну сторону: `client` → `data` и `core`, `data` → `core`, `cli` → `data` и `core`. Клиент читает файлы контента через пакет данных (согласовано владельцем 2026-11-11). Пакет данных берёт из ядра описание карты и её проверку по смыслу, чтобы схема файла и правила ядра не расходились. Ядро не знает ни о Phaser, ни о React, ни о браузере, ни о Node.

Пакеты подключают друг друга прямо исходниками на TypeScript (`exports` указывает на `src/index.ts`), отдельной сборки пакетов нет. Собирается только клиент, через Vite.

## Что сейчас есть в коде

Ядро (`packages/core/src/`), по спецификациям из `docs/mechanics/`:

- `types.ts` — состояние, команды, события, коды отказа.
- `game.ts` — создание партии из описания карты и сида.
- `commands.ts` — `applyCommand` (единственный способ изменить состояние) и `replay` (повтор партии).
- `map.ts` — местность, правила шага, проверка описания карты.
- `movement.ts` — команда «переместить героя».
- `time.ts` — команда «закончить ход» и календарь.
- `pathfinding.ts`, `heap.ts` — поиск пути: обратный поиск от цели, затем выбор шагов по порядку направлений.
- `render.ts` — текстовый вывод состояния и событий.
- `hero.ts` — опыт и уровни героя; `guards.ts` — зона охранника, слова о численности, недельный рост; `mapBattle.ts` — начало боя внутри партии и перенос его итога на карту; `mapContent.ts` — проверка армий и охранников в файле карты; `battleAuto.ts` — команда компьютера за охранника и «бой до конца»; `events.ts`, `renderEvents.ts` — события партии и их текст (этап 3, `21`–`23`).
- `testkit.ts` — помощники тестов: состояние по рисунку из спецификации.

Остальное:

- `packages/data/src/map.ts`, `scenario.ts` — схемы и разбор файлов карты и сценария.
- `packages/cli/src/` — `scenario.ts` проигрывает сценарий, `files.ts` читает файлы, `main.ts` — запуск из консоли (`pnpm run play`).
- `data/maps/` — карты, `data/scenarios/` — сценарии; каждый сценарий автоматически проигрывается как тест.
- `data/defaults.yaml` — начальные значения из контента для сохранений других версий (армия героя); разбор — `packages/data/src/defaults.ts`.
- `packages/core/src/rng.ts` — детерминированный генератор случайных чисел (алгоритм mulberry32). Состояние генератора — обычный объект, который будет храниться в игровом состоянии. Функции возвращают значение и новое состояние, ничего не меняя на месте.
- `packages/data/src/parse.ts` — `parseContentFile`: разбирает текст файла (JSON или YAML по расширению), проверяет по схеме Zod и возвращает либо данные, либо список ошибок с именем файла и поля. С диска не читает.
- `packages/client` — экран карты, см. раздел «Клиент» ниже.



Пакет `cli` запускается прямо из исходников: Node 22 сам отбрасывает типы TypeScript.

## Клиент: холст и интерфейс

На странице два слоя: `#game` (холст Phaser) и `#ui` (вёрстка React поверх холста). Слой интерфейса сам не перехватывает нажатия; перехватывают только кнопки.

Между ними стоит партия — `packages/client/src/game/session.ts`. В ней нет ни Phaser, ни React:

- хранит состояние игры и выбранную клетку с путём до неё;
- принимает действия игрока (касание клетки, конец дня) и превращает их в команды ядра;
- сообщает подписчикам новый снимок и события команды.

Сцена и вёрстка подписаны на партию и друг друга не вызывают. Правил игры нет ни в партии, ни в сцене: путь ищет ядро, команды проверяет ядро.

Файлы клиента:

- `main.tsx` — запускает React.
- `ui/App.tsx` — держит партию и холст Phaser; при смене карты начинает партию заново.
- `game/maps.ts` — читает файлы карт через пакет данных и создаёт партию.
- `game/frameMeter.ts`, `ui/FrameCounter.tsx` — счётчик кадров и номер сборки.
- `save/saveStorage.ts` — хранилище сохранений: файлы на Android, хранилище браузера в превью.
- `save/saver.ts` — очередь записи в две копии.
- `diagnostics/dump.ts` — сбор и выгрузка дампа; `diagnostics/errorScreen.ts` — экран «Что-то пошло не так» (без React, чтобы работал и при падении интерфейса).
- `ui/Dialog.tsx` — окна: стартовый экран, меню, подтверждения.

Формат сохранения и дампа — в пакете данных (`packages/data/src/save.ts`, `dump.ts`, `state.ts`, `stateSchemas.ts`): им пользуются и клиент, и консоль. Работы с хранилищем там нет.
- `game/session.ts` — партия на экране.
- `game/mapScene.ts` — сцена карты: местность (слой плиток), герои, показанный путь, ход героя по клеткам.
- `game/cameraControl.ts` — перетаскивание, щипок, колесо мыши; отличает касание от перетаскивания.
- `game/geometry.ts` — размеры клетки, масштаб, пересчёт координат, границы камеры.
- `game/stubs.ts` — заглушки (догма 14): цвета и фигуры, нарисованные кодом.
- `ui/Hud.tsx` — дата, запас хода, кнопка «Конец дня».

## Android

- Упаковка — Capacitor 8. Настройки — `packages/client/capacitor.config.ts`; проект Android — `packages/client/android/` (создан командой `cap add android`, хранится в репозитории).
- Проект Android руками не правится без нужды: `cap sync android` копирует в него сборку клиента и обновляет служебные файлы.
- APK собирает `.github/workflows/android.yml` на каждый коммит: сборка клиента, `cap sync android`, `gradlew assembleDebug`. Файл попадает в артефакты запуска и в выпуск `android-latest`.
- Отладочные сборки подписаны открытым ключом `android/app/debug.p12` (настройка — в `android/app/build.gradle`). Файл не удалять и не пересоздавать: иначе обновление перестанет ставиться поверх.
- В песочнице агента собрать APK нельзя: нет Java и Android SDK.

## Как догмы проверяются автоматически

Всё это запускает одна команда `pnpm run check`; её же запускает CI на каждый коммит.

| Догма | Проверка |
|---|---|
| 5. Ядро отделено | `scripts/check-boundaries.mjs`: у ядра нет зависимостей, его код импортирует только соседние файлы. Линтер запрещает в ядре `phaser`, `react`, `node:*`, `window`, `document`. Проверка типов: ядро собирается без типов браузера и Node. |
| 7. Детерминизм | Линтер запрещает в ядре `Math.random`, `Date`, `performance`, таймеры и `crypto`. Тест генератора сверяет значения с эталоном, посчитанным отдельной реализацией. |
| 8. Контент в данных | `parseContentFile` и его тесты: ошибка называет файл и поле. Тест проверяет каждый файл в `data/maps/`; каждый файл в `data/scenarios/` проигрывается. |
| 9. Тесты | `vitest run` в составе общей проверки. |
| 11. Простой код | Knip ищет неиспользуемые файлы, экспорты и зависимости. Линтер ограничивает файл 300 строками и запрещает `any` и циклические импорты. |

| 6. Команды | Тесты: отказ не меняет состояние, команда не меняет переданное состояние; тесты свойств на случайных картах. |
| 7. Повтор | Тесты: повтор партии дважды даёт одно и то же; состояние переживает превращение в JSON и обратно. |
| 13. Скорость | `packages/cli/src/budget.test.ts`: поиск пути на 144×144 и применение команды укладываются в бюджет; с этапа 3 — путь и команды на карте 72×72 с охранниками. |
